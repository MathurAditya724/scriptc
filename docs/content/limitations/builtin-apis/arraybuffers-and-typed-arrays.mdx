- **ArrayBuffers and typed arrays:** ArrayBuffers support shared typed-array and DataView storage.
  `new ArrayBuffer(length, { maxByteLength })` creates a resizable buffer: `resize`, `maxByteLength` and `resizable` compile, views created without a length track the buffer's length, and a view that the buffer no longer covers reads as length 0 and throws Node's TypeError from typed-array and DataView methods.
  A resizable buffer reserves `maxByteLength` bytes when it is created, so a `maxByteLength` larger than the memory the system can reserve throws `RangeError: Array buffer allocation failed`, where Node reserves address space only.
  `transfer`, `transferToFixedLength`, growable SharedArrayBuffers, and BigInt arrays are unsupported.
  `Float16Array` stores IEEE 754 half-precision values, rounding each stored number to nearest-even as Node does; `Math.f16round`, `DataView.prototype.getFloat16` and `setFloat16`, and `util.types.isFloat16Array` compile.
  Numeric typed arrays and Buffers preserve their kind and shared storage through `unknown`, including when nested in records and arrays.
  Numeric typed-array constructors can be stored and used with `new`, including constructors read from an array's `constructor` property.
  JavaScript numeric-array parameters and returns preserve typed-array storage.
  `Buffer.from`, `Buffer.allocUnsafe`, and `Buffer.concat` return views into a per-thread pool of `Buffer.poolSize` bytes (64 KiB by default) when the size is below `Buffer.poolSize >>> 1`, as in Node; a pool slab stays in memory while any of its Buffers does.
  Node's own startup code allocates from the first slab, so the `byteOffset` of Buffers in that slab differs from Node's.
  Buffers returned by other Node APIs, such as `fs.readFileSync` and `zlib`, own their `ArrayBuffer`, where Node allocates small ones from the pool.
